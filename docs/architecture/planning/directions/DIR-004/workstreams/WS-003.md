# WS-003. Configured metric workspace

L2 accepted outline `1.0.0`, 2026-09-17, under [DIR-004 2.1.1](../direction.md).

child's scope. WS-003/DEC-01 and DEC-02 record this selection. Acceptance covers

## Outcome and implementation overview

An analyst configures several metric cards inside a report, changes common and
card-specific filters, compares real results, saves the configuration and reopens
the same result bindings. Monitoring goals and authorized shared worksets extend
this same workspace through later bounded children.

| Field | Definition |
|---|---|
| Included | Ordered worksets; independent card instances bound to registered metric versions; catalog/search/order; context inheritance and intersection; Apply/Save distinction; typed comparisons; exact saved configuration/results; later monitoring goals and explicit shared writes |
| First child | Personal report worksets with the existing three receipt metrics and store/date context, real temporal/two-card comparisons, persistence and the accepted pilot composition |
| Deferred | Goals to C02; shared-workset writes to C03; full administration, source setup, segment lifecycle, arbitrary formulas, campaigns, scheduling, publication and export remain in their existing directions |
| Reuse | Six-table PostgreSQL intake, admitted immutable inputs, registered metrics, Analytics results, report revisions/snapshots, Identity permissions, React/native-pilot bridge and existing ECharts |
| Constraints | Server-owned calculations; one application and existing context boundaries; no new service, data/chart library or generic UI engine; local integration and acceptance, packaging separately |
| Depth | One L2 with three selected milestone outcomes; no nested workstreams or duplicated execution journal |

The confirmed C01 scope is personal worksets inside a report; creation/copy and
card selection/order; net revenue, receipt count and average receipt; common
date/store filters plus per-card store filters; same-dates previous-year and
two-card comparisons; server calculations; saved/reopened configuration and exact
results; the accepted composition and local verification. Customer and Product
remain in the six-table source; additional metrics over them are outside C01.

## Contract and sequencing decisions

These are implementation recommendations for L3, not accepted wire schemas.
The [authoring contract, version 8](../../../../../contracts/analytical-authoring-contract.md#metric-worksets-and-monitoring-goals-target-amendment)
and the normative blueprint retain semantic authority.

| Boundary / owner | Recommendation and rationale | Alternative / consequence | Impact and required proof |
|---|---|---|---|
| Configuration — Presentation | Stable workset/card IDs inside a versioned analytical document; card references an immutable MetricVersion and typed parameters. Preserve explicit Apply versus durable Save and report revision CAS | Independent workset service/store adds lifecycle and synchronization without a demonstrated need; reject it for this slice | Proposed compatible extension; exact legacy reader/writer and schema mapping must be fixed in C01 L3 |
| Effective context — Analytics | Normalize common context ∩ card constraints on the server. Include dataset/metric versions, effective filters, period and access policy in result identity. Reuse the current calculation for equal normalized contexts | Browser calculation or local filters that broaden common scope would change meaning; reject | New typed adapter/projection; prove duplicate-card independence, inherited/local identity and disjoint-filter no-data behavior |
| Catalog — Semantic Model | First child uses net revenue, receipt count and average receipt with the real allowed store/date controls; no duplicate formula is created by copying a card | Arbitrary formula/department catalogs broaden the calculation contract and are deferred | Existing formulas/units remain stable; Customer/Product intake stays available, not falsely advertised as new metrics |
| Comparison — Analytics / Presentation / Web | First temporal mode reuses same dates previous year; two-card mode requires compatible time/grain and labeled units. Server comparison projections supply absolute/relative deltas and unavailable reasons; ChartSpec only renders them | Prototype arithmetic or silently fabricated baseline series cannot prove reproducible comparisons | Versioned comparison/ChartSpec extension. No relative delta when denominator is zero/missing; no percentage-point display for non-percentage metrics. Align chart/table/tooltip and saved identities |
| Goals — Analytics calculation, Presentation binding, Identity access | Proposed initial direction is at-least-target. Revenue/count use whole-period totals; average receipt uses revenue/count over that period, never sum/mean of displayed ratios. Store an explicit goal period and version material target/context edits | Treating every goal as a sum or editing past meaning in place is invalid. Whether the initial subset also needs at-most-target is an owner choice before C02 | Proposed only; C02 L3 fixes ownership, progress policy and migration. Missing/partial actuals remain explicit and do not become zero or completion |
| Shared scope — existing Identity + Presentation | First prove private saving; add shared writes only with explicit grants, version conflicts and private overrides in C03 | Building full user/admin workflows first contradicts the selected product-first sequence | Shared contract not yet selected; C03 requires real multi-principal evidence. No changed policy is inferred from a visual selector |

### Compatibility, migration and recovery

Keep current saved reports and immutable artifacts readable. C01 L3 must specify
an explicit legacy-to-configured view and a versioned write path; saving an edited
legacy report creates a new revision and never rewrites its old snapshot.
Validate every result binding at save/reopen. A failed card calculation must not
partially commit a new report version or present old values as freshly calculated.
Preserve request idempotency and revision conflicts; retry only under those contracts.

Prefer an additive storage/contract change. Its exact shape, accepted older
clients, and recovery reader are a C01 design task, not proof already supplied.
Do not promise that an old binary can read new document versions or drop new
columns to simulate rollback. No deployment or accepted installation is changed
by this plan. No new queue, worker or scheduler is selected merely for UI editing.
Evidence uses bounded synthetic test inputs and omits credentials/session data.
